## 4. Architecture audit

### Strengths

- `configs/` separates core paths, training defaults, and experiment definitions.
- `processing_own_phase/` separates Data, Model, Training, Experiment, Evaluation, Final Evaluation, Persistence, and Visualization concerns.
- Checkpoints carry model state, architecture, and training-strategy metadata.
- `runs/<run_id>/` isolates logs, histories, TensorBoard files, and checkpoints by experiment.
- The notebook does not duplicate the training loop; it calls reusable modules or reads artifacts.
- A machine-readable `confusion_matrix.csv` allows consistency checks without extracting values from PNG files.
- Persistent run logs provide evidence that official E1/E2 training used the `mps` backend.

### Architecture risks

#### A-01 — Legacy `main.py` can overwrite final artifacts

**Severity:** High

**File:** [`processing_own_phase/main.py`](../../processing_own_phase/main.py)

`run_full_pipeline()` currently:

1. iterates over the two retained entries in `EXPERIMENTS`, E1 and E2;
2. selects a model through its own legacy logic;
3. creates and evaluates a Test DataLoader;
4. writes `outputs/summary.json` using a schema different from `final_evaluate.py`.

This path is not aligned with the official controlled E1/E2 and guarded single-Test workflow. Running it can make the notebook fail or display noncanonical results.

**Recommendation:** refactor `main.py` into a coordinator that calls `run_controlled_experiments()` and `regenerate_final_artifacts()`, or rename it to `legacy_main.py` and prevent it from overwriting canonical artifacts.

#### A-02 — Two competing `summary.json` schemas

**Severity:** High

`main.py` and `final_evaluate.py` can produce different structures at the same output path. The demo notebook expects the guarded schema containing `validation_verification`, `selection_source`, `test_evaluation_count`, checkpoint hash, and macro metrics.

**Recommendation:** define one versioned summary schema, for example `summary_schema_version: 1`, and validate it before notebook consumption.

#### A-03 — Experiment scope restricted to E1/E2

**Status:** Resolved

The general experiment configuration contains only E1 `head_only` and E2 `partial_finetune`. Additional exploratory experiment definitions and artifacts have been removed.

**Recommendation:** keep future exploratory work outside the canonical configuration and artifact directories.

## 5. Data audit

### Split correctness

- CIFAR-10 official training pool: 50,000 images.
- Internal Train: 45,000.
- Internal Validation: 5,000.
- Official Test: 10,000.
- Split seed: 42.
- Train and Validation indices are disjoint.

### Leakage controls

- An untransformed training dataset is used only to determine size and split indices.
- Train and Validation use separate `datasets.CIFAR10` objects.
- Train uses Resize, RandomCrop, RandomHorizontalFlip, ColorJitter, ToTensor, and Normalize.
- Validation and Test use Resize, CenterCrop, ToTensor, and Normalize.
- TorchVision transforms are lazy and run only when a sample is accessed.

### Audit note

ImageNet mean and standard deviation are fixed constants associated with pretrained weights. They are not statistics fitted from the combined CIFAR-10 splits. If future work switches to CIFAR-specific normalization, mean and standard deviation must be estimated from the Train subset only.

## 6. Model audit

### Controlled strategies

- E1 `head_only`: only classifier `fc` parameters receive gradients.
- E2 `partial_finetune`: ResNet18 `layer4` and classifier parameters receive gradients.
- Backbone family, initial pretrained weights, split, seed, batch size, optimizer, learning rate, scheduler, epoch budget, augmentation, and loss are held constant.

### BatchNorm caveat

Setting `requires_grad=False` freezes parameters but does not automatically freeze BatchNorm running mean and variance while the whole model is in `train()` mode. Therefore, `head_only` is exact at the gradient-parameter level but may not be exact at the model-buffer level.

**Recommendation:** for a stricter ablation, keep BatchNorm modules in frozen backbone blocks in `eval()` mode throughout training, and retrain both strategies under the same policy.

## 7. Training audit

Per-epoch history contains:

- `train_loss`;
- `train_acc`;
- `val_loss`;
- `val_acc`;
- `lr`;
- `epoch_time`.

Training uses `model.train()`. Validation uses `model.eval()` with an inference/no-gradient context. The pipeline implements Validation-based best checkpointing, Early Stopping with patience 3, ReduceLROnPlateau, and gradient clipping.

Official E1 and E2 each ran for five epochs on the Apple GPU through MPS. E2 reached its best Validation Accuracy at epoch 4; the final epoch declined slightly, which confirms that using `best.pt` rather than the final in-memory state is necessary.
